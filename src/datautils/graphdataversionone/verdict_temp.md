# Audit verdict — `src/datautils/graphdataversionone/`

Reviewed against `DATASET_PLAN.md` and `README.md`. Method: read every `.py` file line by line,
cross-checked the connectivity math against the installed `mne-connectivity==0.9.0` source, ran the
16-test suite, and ran `validation.py` against the actual generated dataset at
`data/moabb/Graph-Liu2024-VersionOne/` (2000 trials, 50 subjects, already on disk).

**Overall: the numerical pipeline is sound.** Every claim I could independently verify (CSD sphere
fitting, the `_foi_average` band-doubling bug, wPLI/PLV/iCoh formulas, CUDA/CPU formula parity, edge
ordering, save/load round-trip) checked out exactly against ground truth. The one real problem is not
in the math — it's that **the shipped verification artifacts are no longer reproducible by the checked-in
code**, which undermines the audit trail the plan asks for. Details below, most important first.

## 1. `validation_report.json` / `CUDA_VALIDATION.json` cannot be regenerated by the current code (High)

The dataset on disk ships `data/moabb/Graph-Liu2024-VersionOne/validation_report.json` with fields
`status`, `checks`, `node_variants`, `edge_variants`, `window_length_counts`, and — the important one —
`cpu_reference_spot_checks` (per-trial max-abs-error of the CUDA backend against the CPU/MNE reference
at each of the three observed window lengths, 2000/2001/2002 samples). `CUDA_VALIDATION.json` similarly
records float64 max-abs-errors between the two backends for 6 specific trials.

I grepped the entire package for the strings that build these fields
(`cpu_reference_spot_checks`, `window_length_counts`, `status`, `checks`) — they appear **nowhere** in
`validation.py`, `generate_dataset.py`, or any other file. `validate_saved_dataset()` as it exists today
([validation.py:236-336](validation.py#L236-L336)) returns only
`n_samples`, `n_subjects`, `subject_counts`, `class_counts`, `subject_class_counts`; `main()` in
`generate_dataset.py` ([generate_dataset.py:219-221](generate_dataset.py#L219-L221)) only adds
`elapsed_seconds` on top of that. I ran it live against the real output directory and confirmed this —
the current tool only prints those five keys, nothing about CPU/CUDA agreement or window-length spread.

So the CPU-vs-CUDA numerical cross-check that the README explicitly leans on ("CPU-reference spot checks
... matched the saved float32 features exactly. Details are in the output directory's
`validation_report.json`", [README.md:71](README.md#L71)) was performed by a script that is not part of
this directory and cannot be re-run today. If the CUDA backend is ever touched again, there is no
committed way to reproduce that verification — you'd be trusting a stale JSON file, not a check the repo
can still run. `test_connectivity_backends.py` doesn't fill this gap either: its only test
(`test_explicit_band_bounds`) mocks `spectral_connectivity_time` entirely to check band-boundary
arithmetic — it never touches `connectivity_cuda.py` or does a real CUDA-vs-CPU comparison. There is
**no regression test** guarding the two backends' numerical agreement.

This isn't a correctness bug in the shipped arrays (I re-ran the current, weaker validation against them
and it passes — see below), but it is a real gap between what's documented/claimed and what the code in
this directory can actually do, and it's the kind of thing that will bite silently the next time someone
edits `connectivity_cuda.py` or `edge_features.py`.

**Fix**: either restore a `--check-cuda`/spot-check code path in `validation.py` (or a small dedicated
script) that regenerates `cpu_reference_spot_checks` and can be run as part of `generate_dataset.py`'s
final validation, and/or add a real (non-mocked) unit test that runs `compute_connectivity` and
`compute_connectivity_cuda` on the same synthetic signal and asserts near-equality when CUDA is
available (skip otherwise, like `test_source.py` already does for missing local data).

## 2. `save_dataset` keeps only subject 1's montage record, with no cross-subject check (Low)

[storage.py:69](storage.py#L69): `metadata_builder(samples, [row['provenance'] for row in sidecars],
sidecars[0]['montage'], arrays)` — every subject's checkpoint carries its own computed `montage` dict
(built per-subject in `generate_subject_features` via `build_montage_metadata`), but only the first
subject's copy is written to the final `metadata.json`; the other 49 are silently discarded.

In the current implementation this is safe: `build_montage_metadata` only depends on the fixed channel
order and the one dataset-wide electrode TSV (`files/38516078`), not on anything subject-specific, so
all 50 copies are provably identical today. But there's no assertion that enforces this — if a future
change ever made montage computation subject-dependent (e.g. per-subject digitized positions), this
silent discard would hide a real divergence instead of failing loudly, which cuts against the plan's own
principle ("A failure must identify its subject/trial; do not silently omit a sample from only one
variant", [DATASET_PLAN.md:93](DATASET_PLAN.md#L93)) — montage isn't a "sample", but the spirit is the
same.

**Fix**: assert all `sidecars[i]['montage']` are equal before discarding, or drop the redundant
per-subject computation and construct montage metadata once outside the per-subject worker.

## Verified correct (not exhaustive, but the parts most likely to hide a subtle bug)

- **`_foi_average` band-doubling bug is real**, confirmed by reading the installed
  `mne_connectivity/spectral/time.py:1521-1523`: `f_e += 1 if f_s == f_e else f_e` doubles the upper
  index for any multi-bin band instead of incrementing it. The code's workaround —
  `faverage=False` plus explicit inclusive-band averaging in
  [edge_features.py:110-114](edge_features.py#L110-L114) — is the correct fix and is exercised by
  `test_connectivity_backends.py`.
- **wPLI/PLV/imaginary-coherence formulas** in `edge_features.py` and the CUDA reimplementation in
  `connectivity_cuda.py` match `mne_connectivity`'s own `_wpli`/`_plv`/`_imcoh` bivariate estimators
  exactly (verified line-by-line against `time.py`). Both are already non-negative per frequency bin by
  construction (`abs()` is baked into the numerator), so the `[0, 1]` clipping in the code is pure
  floating-point-noise protection, not silently masking sign errors.
- **CSD sphere fitting** ([preprocessing.py:138-141](preprocessing.py#L138-L141)) reproduces MNE's own
  `sphere='auto'` branch inside `compute_current_source_density` bit-for-bit
  (`x, y, z = origin_head - origin_device`) — confirmed by reading MNE's source, and independently
  exercised by `test_source.py::test_csd_matches_mne_auto_and_preserves_eeg` with `atol=0, rtol=0`.
- **Edge index / reverse-direction symmetry**: `build_edge_index` (upper triangle + reversed pairs) and
  `build_edge_features`'s symmetric-adjacency indexing are internally consistent and covered by both
  `test_features.py` and `test_dataset.py`'s asymmetry-rejection tests.
- **Full pipeline round-trip**: I ran `python -m src.datautils.graphdataversionone.validation
  data/moabb/Graph-Liu2024-VersionOne` against the real, already-generated 2000-trial/50-subject dataset
  and it passed cleanly — all shapes/dtypes, entropy/connectivity ranges, reverse-edge equality, and
  label/subject/trial alignment check out on the actual data, not just synthetic fixtures.
- **Marker decoding** (`source.py::read_trial_table`) correctly disambiguates subject 43's two extra
  post-break code-2 pulses and subject 13's fractional marker tail; both are covered by real-data
  regression tests in `test_source.py` and pass.
- All 16 unit tests pass (`pytest src/datautils/graphdataversionone/` → `16 passed, 11 subtests passed`),
  matching the README's claim.

## Minor observations (not bugs)

- `metadata.py`'s `db_reference_si: 1e-12` is correct for *both* node variants even though the physical
  quantities differ (V² vs (V/m²)²) — "micro" always contributes `(1e-6)² = 1e-12` regardless of the base
  unit's dimension, so a single shared numeric reference is not an inconsistency.
- Nothing in `node_features.py`, `edge_features.py`, or `preprocessing.py` mutates its input arrays in
  place; every function that claims immutability in its docstring actually holds to it.
